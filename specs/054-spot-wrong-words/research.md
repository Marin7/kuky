# Research: Spot the Wrong Words

All Technical Context items were resolved from the existing codebase; no open
NEEDS CLARIFICATION remain.

## R1 — New question kind vs. new homework type

- **Decision**: New `QuestionKind.SPOT_WRONG_WORDS`, structured (`isStructured()` = true).
- **Rationale**: All three surfaces (homework, activities, quizzes) share `QuestionKind`, `HomeworkAdminService` validation (activity and quiz admin delegate to it), `QuestionScoring` (homework and quiz) and the front-end `QuestionEditorCard` / `ExerciseForm` / `MixedHomeworkForm` / `ExerciseResult`. A kind gives FR-001/FR-017 and the mixed-homework lifecycle (`HomeworkCompositionSupport` treats every non-`FREE_TEXT` kind as auto) without extra work.
- **Alternatives**: a new `HomeworkType` (like `WRITE`) — rejected: it couldn't be mixed with other questions and would need its own flows.

## R2 — Kind name and DB constraint

- **Decision**: `SPOT_WRONG_WORDS` (16 chars, fits `VARCHAR(20)`). Migration `V27__spot_wrong_words_kind.sql` drops and re-adds `homework_questions_kind_check`, `activity_questions_kind_check`, `quiz_questions_kind_check` with the new value appended (same pattern as V9/V15).
- **Alternatives**: `WRONG_WORDS`, `SPOT_ERRORS` — less clear next to the spec terminology.

## R3 — Where the passage lives

- **Decision**: The passage is the question `prompt` (required and non-blank already), exactly as for `MULTI_BLANK` / `DRAG_DROP`. The prompt label is hidden in student rendering (`hidesPromptLabel`), and the instruction "Encuentra los N errores" is generated by the UI. Max 3,000 characters is enforced in `validateSpotWrongWords`.
- **Rationale**: `prompt` is `NOT NULL` and validated non-blank; adding a separate text field would duplicate it. Spec FR-002 updated accordingly.
- **Alternatives**: `structure.text` + prompt as instruction — rejected: forces the teacher to write an instruction for every question and makes the prompt-snapshot paths carry two texts.

## R4 — Word segmentation (FR-006)

- **Decision**: A word is the regex
  - TS: `/[\p{L}\p{M}\p{N}]+(?:['’-][\p{L}\p{M}\p{N}]+)*/gu`
  - Java: `Pattern.compile("[\\p{L}\\p{M}\\p{N}]+(?:['’\\-][\\p{L}\\p{M}\\p{N}]+)*")`

  Words are numbered 0…n-1 in order of appearance. Everything between matches is a non-selectable gap (whitespace, punctuation, newlines kept verbatim so paragraphs render).
- **Rationale**: Covers accented letters/ñ (`\p{L}`), decomposed accents (`\p{M}`), numbers (`\p{N}`), internal hyphen/apostrophe including the typographic `’`; `¿Dónde?` → `Dónde`; a dash surrounded by spaces is a gap.
- **Drift control**: The client is the only place that turns indices into words for display, and it uses one function (`lib/spotWrongWords.ts#tokenize`) for editor, preview, student form and results — so the student always sees the teacher's segmentation. The server tokenizes only to validate a save: each error's `wordIndex` must be in range **and** the token at that index must equal the stored `word`. If the two regexes ever disagreed, saving fails with a clear message instead of storing a wrong key. Shared vectors (see data-model) are asserted in `SpotWrongWordsTest`; the front-end has no unit-test runner, so the same vectors are checked in quickstart scenario 1.
- **Alternatives**: server returns pre-segmented `segments[]` to students — rejected: the editor and preview still need client tokenization, so it would add a second source of truth without removing the first.

## R5 — Answer-key storage

- **Decision**: `structure_json = { "errors": [ { "wordIndex": int, "word": string, "correction": string|null } ] }`, sorted by `wordIndex`, unique indices, 1–30 entries; corrections trimmed, blank → `null`, ≤100 chars.
- **Rationale**: Index identifies the occurrence (spec: repeated words are independent); `word` is the drift guard and makes `Errores frecuentes` / results readable even without re-tokenizing.
- **Student view**: `stripStructureForStudent` returns `{ "errorCount": n }` only (FR-009).

## R6 — Student answer, cap and submission

- **Decision**: `answerJson = { "selected": [wordIndex…] }`. Client enforces the cap (FR-008a): toggling on is ignored at `selected.length === errorCount`, and an inline hint is shown. Server, in `SpotWrongWords.grade`: drop non-integers and out-of-range indices, de-duplicate; if the remaining count > `errorCount` → `IllegalArgumentException` ("Has marcado más palabras que errores.") → `VALIDATION_ERROR` 422, which aborts the whole submission (nothing persisted, matching how other invalid submits behave).
- **Drafts**: none. The per-homework `localStorage` draft (`homeworkDraftKey`) only covers free-text answers (`ManualAnswerForm`); no auto-graded kind persists unsubmitted answers, so this kind matches them (spec edge case corrected during implementation).

## R7 — Scoring and result units (FR-012/13/14)

- **Decision**: `score = found / errorCount` (one contribution in `HomeworkCompositionSupport.contributions`, like `MULTI_BLANK`; fully correct only at 1.0). `unitResults` lists, ordered by word index:
  - error found → `index=wordIndex, score=1, correct=true, studentDisplay=word, expectedDisplay=[correction] or []`
  - error missed → `index=wordIndex, score=0, correct=false, studentDisplay=null, expectedDisplay=[correction] or []`
  - wrongly marked correct word → `index=wordIndex, score=0, correct=false, studentDisplay=word, expectedDisplay=[], label="EXTRA"`
- **Rationale**: Reuses `UnitResultDto` unchanged (homework, activity and quiz result DTOs all embed it). `label="EXTRA"` makes the third state explicit rather than inferred. The overall question score is computed from errors only, never by averaging units.
- **Alternatives**: new DTO fields (`markedWordIndices`) — rejected: three result DTOs and their TS twins would change for one kind.

## R8 — Activities grader

- **Decision**: `ActivityExerciseGradingService` keeps its own switch (it duplicates `QuestionScoring` today); its new case delegates to `SpotWrongWords.grade(...)`, and its `stripStructureForStudent` gets the same `{ errorCount }` case. Refactoring the activity grader onto `QuestionScoring` is out of scope.

## R9 — Snapshot / later edits (FR-015)

- **Decision**: No new work. Homework submissions are judged against `assignment_snapshot` (V20), quiz attempts against `QuizSnapshot`, and stored per-question scores are never recomputed (`recomputeUnitResults` rebuilds only unit feedback). The new kind flows through the same paths because its key lives in `structure_json`.

## R10 — Keeping marks while editing the text (FR-002b)

- **Decision**: Editor-only logic in `lib/spotWrongWords.ts#carryMarks(oldTokens, newTokens, oldErrors)`: compute an LCS over the two token-text arrays; each old error whose token is matched keeps its correction at the new index; unmatched ones are dropped. Run on every text change (debounced not needed at ≤3,000 chars).
- **Rationale**: "Marks stay on words that still exist unchanged, even if their position shifts" — LCS is the standard minimal-diff matching; O(n·m) on ≤~600 tokens is trivial.

## R11 — Errores frecuentes (FR-016)

- **Decision**: No back-end change: `StudentMistakesAdminService.answeredAndWrong` already counts any non-numbered kind once and lists it when `!result.correct()`. `MistakeOnlyDetail.tsx` gets a branch that renders `SpotWrongWordsResult` (compact) from the snapshot question + unit results. Spec US3 updated: the question counts as one mistake.

## R12 — Localisation

- **Decision**: New UI strings in `es`, `en`, `ro` locale files (kind name "Encontrar errores" / "Spot the mistakes" / "Găsește greșelile", counter, cap hint, legend). Server validation messages in Spanish like the existing ones. Spec FR-018 updated to match the site's three locales.
